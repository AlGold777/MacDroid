# ТЗ для модели-исполнителя: Production Transport v1

## Задача и источник

Реализуй в текущем MacDroid Commander устойчивый и измеряемый транспорт Mac ↔ Android на стандартном SSH/SFTP. Исходная концепция: `MacDroid — Production Transport Architecture v1` из приложенного пользователем плана. Этот документ адаптирует её к **текущему коду** и задаёт порядок работы, инварианты и проверяемые результаты. Перед правками прочитай исходный план, `README.md`, `docs/architecture_brief.md`, `docs/product_spec_v3.md` и актуальный код. Старый `docs/ТЗ_для_LLM.md` описывает прежний прототип и содержит устаревшие утверждения о mock-транспорте; не принимай его за описание текущего состояния.

Работай в корневых `MacHost/` и `AndroidCompanion/`; вложенная копия `mac_android_filemanager_v2/` не является целью реализации. **Сначала проверь `git status` и существующие diff**: рабочее дерево содержит пользовательские изменения, их состав может измениться. Не сбрасывай, не stash и не включай чужие правки в свои коммиты. Отдельная ветка или worktree допустимы только с сохранением границ этих изменений. Каждое самостоятельное законченное изменение фиксируй отдельным коммитом, не накапливая весь этап; перед рисковыми переделками ставь тег. После изменения кода подними версии во всех связанных файлах версионирования (`MacHost/Resources/Info.plist`, `AndroidCompanion/app/build.gradle.kts`, а также других, если сборочные скрипты задают версию) и обнови документацию функциональности. Стадируй файлы или hunks выборочно.

## Фактическая отправная точка

| Узел | Что есть сейчас | Что требуется |
| --- | --- | --- |
| `MacHost/.../Transport/SSHControlClient.swift` | Запускает системный OpenSSH как `ssh -s sftp`; один процесс даёт один SFTP channel. `sendSFTPPacket` последовательно пишет пакет и читает следующий ответ. | Единый владелец чтения pipe, разбор и доставка ответов по `requestId`, безопасные concurrent operations, явное управление жизненным циклом. Не реализуй второй SSH stack на базе `SSHProtocolHandler.swift`: он не является действующим transport. |
| `TransportMultiplexer.swift` | Download/upload уже посылают до 4 запросов, chunk 256 KiB. Операции вызывают raw read/write напрямую; `READ` сверяет ID лишь частично, `WRITE` не связывает ACK с диапазоном. | Общий session budget, корректная маршрутизация и учёт каждого диапазона, адаптивные параметры после negotiation, безопасная отмена/разрыв. |
| `SFTPPacketEngine.swift` | SFTP v3 и `NAME` attrs уже разбираются. | Парсер `VERSION` extensions, `SSH_FXP_EXTENDED`, limits/statvfs/posix-rename/fsync при наличии, строгая валидация длины и ID. |
| `RemoteSFTPDriver.swift` | Листинг читает `READDIR` последовательно и использует attrs из `NAME`; нет N×`STAT`. Есть ADB fallback, path mapping и операции с файлами. | Сохранить attrs-путь; проверить корректность конкурентного `READDIR` на MINA до включения. Кэш и invalidation. Разделить ошибки транспорта и бизнес-операций. |
| `JobOrchestrator.swift`, `IntentLedger.swift` | Есть SQLite WAL, state machine, `.mcdpart`, проверка размера, rename/backup, повторы download и upload при сетевом сбое в окне ≈60 с с продолжением с frontier (с 2.1.293; раньше — до трёх попыток download). Resume выводится из размера part и сравнения первых 4 KiB; очистка active part может удалить данные для resume. | Отдельный durable transfer journal и contiguous frontier; миграция старых part без доверия к размеру; восстановление commit после сбоя; сохранение существующих conflict/move семантик. |
| `TransferQueueManager.swift` | Очередь/UI pause-resume существуют, но не дают transport-level backpressure. | Ограниченный cross-file scheduler с общими кредитами и совместимой UI-семантикой. |
| `AndroidCompanion/.../server/EmbeddedServer.kt` | Apache MINA SSHD 2.12.0, `VirtualFileSystemFactory(/storage)`, SFTP subsystem, 8 MiB server window. | Доказать поддержку extensions и лимитов; добавить ограничение FS операций и замеры. MediaStore fast path интегрировать только через корректный поддерживаемый extension point. |
| `StorageGateway.kt`, `CustomSftpEventListener.kt` | Room receipt и media scanner при commit. | Согласовать события commit/invalidation с новой temp/rename схемой; не считать receipt доказательством, что байты durable. |

Сохранить USB/ADB и Wi-Fi пути, host-key pinning, миграцию ключей, pairing, path mapping `/storage` ↔ `/emulated/0`, NFC имён, конфликтные стратегии, Mac↔Mac операции, preview и текущие пользовательские изменения. Прямые вызовы `downloadFileStreaming` из `DualPaneViewModel` для preview/Quick Look учесть в приоритетах и в бюджете, а не только вызовы `JobOrchestrator`.

**Главная интеграционная правка:** `RemoteSFTPDriver` и `TransportMultiplexer` сейчас создают **разные** `SSHControlClient`, со своими процессами, счётчиками ID и параметрами подключения. `ConnectionController` управляет подключением driver; transport подключается отдельно и вызывает `connect()` с legacy fallback по умолчанию. Ввести общий владелец соединения, внедряемый в оба компонента: `ConnectionController → SessionCoordinator → SFTPChannel(interactive/bulk)`. Он хранит выбранное устройство, endpoint, trust/auth policy, path mapping, epoch и общий budget. На каждый channel — отдельный dispatcher/reader и пространство request ID. У actor сейчас нет двух одновременно выполняющихся `readRawResponse`; проблема — чередование логических потребителей между отдельными `await`, а также блокирующий pipe I/O внутри actor.

## Обязательные инварианты

1. Считывать байты из одного SFTP stdout вправе только один read loop. Для каждого ответа проверить framing, тип, `requestId`, принадлежность текущей session/channel и наличие pending operation. Неизвестный/дублированный ответ, неожиданный `STATUS` и EOF не могут ошибочно завершить другую операцию. `VERSION` обрабатывается отдельно до request dispatcher. Ограничить максимальный размер входного пакета до выделения памяти.
2. Ни один SSH/SFTP handle не переживает reconnect. При смене endpoint, host key или session epoch все pending запросы завершаются явной ошибкой, кредиты освобождаются один раз, новая session создаёт новые handles. Отмена одного transfer не уничтожает чужой незавершённый запрос; аварийное завершение общей session классифицирует все запросы.
3. На Mac **общий** `SessionBudget` ограничивает ожидаемый payload незавершённых запросов, write buffers, handles и transfers; на Android отдельный серверный limiter ограничивает FS ops для всех channels и сессий. Стандартный SFTP не передаёт клиенту кредиты серверных workers. Считать также pending maps, metadata requests, очереди writer и локального disk I/O: маленькие запросы нельзя накопить без ограничения по количеству. Кредит резервируется до отправки; для READ память остаётся учтённой до записи/освобождения DATA. Отмена или timeout вызывающего кода не отменяет уже отправленный SFTP запрос: оставить его ID и кредит до получения ответа либо teardown channel. До безопасного завершения запроса не переиспользовать ID даже при wraparound. Интерактивным операциям оставить резерв.
4. `READ` и `WRITE` сопоставлять по ID с `{file, offset, requestedLength, epoch}`. Для short `DATA` повторно запросить остаток либо явно завершить ошибкой; нельзя зачесть недополученные байты. Ответы могут прийти вне порядка. Download пишет по смещению (`pwrite` или защищённый аналог); `written == expectedSize` само по себе не доказывает покрытие без дыр.
5. Progress для возобновления берётся из непрерывно подтверждённого диапазона, а не из размера `.mcdpart`, наибольшего ACK или числа отправленных байт. Для download подтверждение означает **успешную запись локального диапазона**; для upload — `STATUS OK` соответствующего `WRITE`. Различать ACK и durable checkpoint.
6. Upload пишется только в уникальный temp path рядом с final, созданный эксклюзивно (`CREAT|EXCL`); resume открывает существующий temp без `CREAT|TRUNC`. До rename проверить размер/целостность temp, получить успешный CLOSE, затем подтвердить final. Для overwrite использовать проверенное атомарное замещение. Цепочка `final → backup → temp → final` имеет окно отсутствия final и не считается атомарным замещением; её нельзя оставлять production fallback. Если нужная семантика недоступна — явный `UNSUPPORTED_ATOMIC_REPLACE` до изменения final; `INDETERMINATE` означает неизвестный результат уже отправленной операции. Политики skip/autoRename не должны перезаписывать файл, появившийся после preflight. При Move повторно проверить источник перед удалением; изменившийся источник сохранить и вернуть соответствующий результат.
7. Кэш листинга служит только UI. `DELETE`, `RENAME`, `OVERWRITE`, `OPEN` и resume требуют актуальной проверки объекта. Ключ кэша включает SSH host-key fingerprint, идентификатор storage/volume и нормализованный path. Не показывать temp файлы как завершённые.

## Этапы реализации

### P0. Надёжная основа, до увеличения глубины конвейера

1. Зафиксируй исходные benchmark и тесты без правок кода; опиши реальные ограничения системного OpenSSH. Для двух SFTP channels в одной TCP/SSH session выбери и проверь практический механизм (например, OpenSSH multiplexing через выделенный ControlMaster/ControlPath и два `ssh -S ... -s sftp` процесса). Если выбранный механизм не доказан end-to-end с Android MINA, оставь один безопасный канал и пометь разделение channels как отдельный незакрытый критерий: не подменяй требование двумя независимыми TCP sessions. Не трогай пользовательские SSH config/key files.
2. Введи общий `SessionCoordinator` и channel-scoped dispatcher с typed request API вместо сочетания `sendSFTPPacket`, `writeRawPacket`, `readRawResponse`. На channel один reader и сериализованный writer, работающие независимо: блокирующий `FileHandle.read/write` нельзя выполнять внутри управляющего actor или на общей последовательной очереди, иначе заполненные pipes взаимно остановят чтение/запись. Используй неблокирующий I/O либо выделенные ограниченные I/O очереди. Зарегистрируй pending request **до** отправки; при ошибке отправки разреши его явно. Мигрируй оба клиента и всех потребителей, добавь тайм-ауты и teardown. Один координатор отвечает за reconnect с bounded backoff; ручной disconnect/cancel запрещает автоматическое переподключение. READY наступает после VERSION, capabilities и root mapping; смена host key требует прежней процедуры доверия, не автоматического resume. Сохрани строгую auth policy после миграции ключей на обоих каналах.
3. Добавь `SessionBudget`: network payload in-flight 8 MiB, write buffers 8 MiB, handles 32, interactive reserve 1 MiB. В P0 оставь максимум один bulk transfer и глубину не выше существующей 4; настройки ускорения активируй в P1/P3 после correctness gate. Целевой READ — 128 KiB × 32 = 4 MiB; WRITE — 128 KiB × 16 = **2 MiB**, при этом high-water 4 MiB является дополнительным потолком, а не целью заполнения. Запрос разрешён, только если одновременно хватает request slots, byte budget и buffers; пополняй после каждого завершения, не жди недостижимых 4 MiB. Если позже включается hysteresis, её low-water должен быть меньше достижимого high-water. Ограничивай chunk также полным размером SFTP packet с handle/заголовками; нулевой limit сервера не трактуй как запрет запросов. Эти правила соответствуют [описанию limits OpenSSH](https://raw.githubusercontent.com/openssh/openssh-portable/master/PROTOCOL). Проверь реальные размеры окна в обоих направлениях; server receive window не задаёт client receive window.
4. Сделай `ConfirmedRangeTracker` и версионируемую схему `TransferJournal` с миграциями. Храни устойчивый transferId, host-key/volume identity, direction, source snapshot, final/temp paths, expected size, диапазоны/frontier, durability evidence и фазу commit. Checkpoint диапазонов и состояния атомарен; ошибки SQLite должны возвращаться исполнителю. Не использовать временную/in-memory БД из текущего UI fallback для обещанного durable resume. Для download порядок durable checkpoint: записать данные → синхронизировать файл → надёжно сохранить frontier; после crash journal не должен утверждать наличие несохранённых байт. Для upload ACK-frontier допустим при сетевом reconnect без потери данных сервером; после возможной перезагрузки Android одних size/mtime недостаточно: проверить сохранённый префикс целиком хэшем/чтением, либо начать безопасно с нуля. Если невозможно подтвердить durability/identity, не возобновлять вслепую. Старые `.mcdpart` без journal не считать доказательством покрытия; сохранять их до безопасного решения. Сбой journal запрещает commit и удаление источника.
5. Приведи transfer к циклу `prepare → transfer → drain → verify → close → commit → complete`; для durable upload выполнить поддерживаемый fsync до CLOSE. Resume идёт с journal frontier, возможный записанный хвост за ним повторяется; полная проверка покрытия обязательна даже при `part.size == expectedSize`. Проверяй snapshot источника при открытии и перед commit; size/mtime — слабая identity, не доказательство неизменности всех байт. Состояние `COMMITTING` сохранить до rename. При потере его ответа сопоставить final/temp и сохранённые доказательства принадлежности transfer: один совпавший размер не разрешает считать rename успешным и удалять источник. При неоднозначности — `INDETERMINATE`. Suspend/pause сохраняют part; cleanup удаляет только доказанно принадлежащие завершённой/отменённой операции файлы, не все старые `.mcdpart` по маске.

**Ворота P0:** тесты с перестановкой ACK, дырой в диапазонах, short read, потерей соединения в каждой фазе, cancellation, stale handle, duplicate response, mismatch source/temp, повторным запуском после rename. Ни одна ошибка не превращается в успех; старая final версия сохраняется при неудачном overwrite. Поставь тег `gate-transport-p0` после зелёных тестов.

### P1. Производительность одиночных файлов и листинга

1. Активируй параметры READ/WRITE из P0.3 только после ворот P0, измеряя RTT, goodput и память. Учти копии payload при сериализации; суммарный RSS будет выше лимита payload. Ни download, ни upload не держат весь файл в RAM. Минимальные счётчики request/bytes/latency нужны уже здесь; P4 оформляет полный benchmark.
2. `RemoteSFTPDriver.listDirectory` продолжает использовать attrs из `NAME`. Запрети N×`STAT` для уже предоставленных полей; отдельный `STAT` допускается лишь при недостающем атрибуте, который действительно нужен UI/операции.
3. Добавь pipelined `READDIR` с depth 4, сохранив последовательное обслуживание directory cursor на сервере. В MINA 2.12.0 requests одного subsystem обрабатывает один `run()` loop; замена executor на pool сама по себе это не меняет. Очередь requests связана с освобождением SSH receive window после обработки — проверь совокупный byte/request backlog, не заменяй её блокирующей очередью на сетевом потоке без анализа deadlock. Это видно в [исходнике SftpSubsystem 2.12.0](https://raw.githubusercontent.com/apache/mina-sshd/sshd-2.12.0/sshd-sftp/src/main/java/org/apache/sshd/sftp/server/SftpSubsystem.java). Проверить 5 000+ уникальных записей, отсутствие пропусков/дублей; после первого EOF прекратить новые READDIR, дождаться всех выданных ответов (включая NAME), затем CLOSE. Feature flag позволяет вернуться к depth 1 при несовместимости.
4. На Android ограничь реальные FS операции и metadata workers: стартовый pool 4, глобальный максимум 8. Worker pool для синхронного accessor не обещает параллельное исполнение WRITE одного subsystem. Для параллельного сбора attrs нужны bounded prefetch/batch и сохранение порядка cursor/CLOSE; глубокая переделка request executor требует отдельного доказательства корректности. Для metadata hook исследуй [SftpFileSystemAccessor 2.12.0](https://raw.githubusercontent.com/apache/mina-sshd/sshd-2.12.0/sshd-sftp/src/main/java/org/apache/sshd/sftp/server/SftpFileSystemAccessor.java); не подменяй через общий accessor авторитетные STAT/FSTAT устаревшими attrs листинга.

**Ворота P1:** контрольные хэши/размеры после передачи, отсутствие стат-шторма, сохранность листинга, bounded memory/handles/FS ops и сравнение throughput с baseline P0 на том же устройстве и сети.

### P2. Android metadata acceleration

Для `DCIM`, `Pictures`, `Movies`, `Music` используй MediaStore как ускоритель получения метаданных: он индексирует доступные media collections и не доказывает полноту произвольного файлового каталога ([Android: shared media](https://developer.android.com/training/data-storage/shared/media)). Перечисляй непосредственные имена и подкаталоги через FS; одним запросом получай MediaStore attrs для этого volume/relative path, сопоставляй по точному имени, недостающие/сомнительные attrs собирай bounded FS workers. Не теряй неиндексированные файлы, `.nomedia`, документы и пустые подкаталоги. Чистый MediaStore-only listing допустим только для явно отдельного media-view, которого в этой задаче нет. SQLite/LRU/observer invalidation ускоряют list; STAT/FSTAT и операции записи остаются авторитетными. Тестируй SD/OTG, разрешения, внешние изменения и обычный SFTP клиент. Для оценки эффекта отдельно посчитай оставшиеся FS metadata calls: быстрый возврат устаревших attrs не считать улучшением корректного листинга.

**Ворота P2:** одинаковые множества и атрибуты для 5 000 файлов при холодном/тёплом листинге, после внешней записи на телефоне, после операций MacDroid и после отключения/повторного подключения SD. Замерь latency MediaStore и FS fallback.

### P3. Отзывчивость и множество файлов

Реализуй macOS L1 memory + L2 SQLite directory cache со stale-while-revalidate, bounded TTL и invalidation после собственных операций. Не используй результаты старого устройства или сменённого host key. При refresh обновляй UI только при изменениях и защищай от ответа для уже покинутого каталога.

Для interactive/bulk traffic используй два доказанно отдельных SSH channels одной session, либо явно зафиксируй технический blocker и измеряемый временный режим с одним dispatcher и reserved credits. Не объявляй ворота P3 пройденными при двух TCP connections вместо одной session. Cross-file scheduler: 4 активных файла, максимум 8 по benchmark, общие клиентские byte/handle кредиты и серверный FS limiter, справедливость, отмена/пауза отдельного задания, сохранение порядка и conflict semantics. Файлы проходят собственные journal/commit независимо; group `COMPLETE` только после всех подтверждённых исходов. Конфликтующие операции с одним final path сериализовать; при рекурсивном копировании создавать родителей до файлов, удалять исходные каталоги Move только после подтверждённых дочерних операций.

**Ворота P3:** при копировании большого файла открытие каталога/preview имеет ограниченную и измеренную задержку; 1 000 малых файлов не создают неограниченных tasks/handles/буферов; pause/resume/cancel одной передачи не повреждают остальные.

### P4. Наблюдаемость и benchmark

Добавь счётчики и логирование без путей, имён файлов, ключей и содержимого по умолчанию: SFTP RTT, READ/WRITE throughput, in-flight bytes, queue wait, SSH channel stalls там, где OpenSSH даёт наблюдаемость, Android FS latency, MediaStore latency, активные FS ops, пиковая память buffers, reconnect, реально сохранённые resume bytes. Если метрику нельзя получить из системного `ssh` без смены transport, явно пометь недоступной; не выводи фиктивное значение. Сценарии: raw TCP, SSH stream, single large upload/download, 5 000-entry list, 1 000 small files, Wi-Fi loss/reconnect. Зафиксируй устройство, версию Android/macOS, USB или Wi-Fi, размер/число файлов, прогрев, несколько повторов, median и диапазон; сравни с исходным baseline. Не обещай конкретный множитель ускорения до замеров.

## Protocol и compatibility правила

- SFTP v3 остаётся базовым wire protocol. Возможности `limits@openssh.com`, `statvfs@openssh.com`, `posix-rename@openssh.com`, `fsync@openssh.com` и server-side hash обнаруживаются по `VERSION`/подтверждённому ответу, а не по предположению, что Android MINA поддерживает OpenSSH extensions. Отсутствие каждой возможности имеет явный fallback. `statvfs` не заменять фиктивным объёмом диска: текущий `RemoteSFTPDriver.checkFreeSpace` возвращает при провале произвольные 280/512 GB. Использовать свежий результат для целевого volume с учётом temp и одновременно зарезервированных передач; отсутствие измерения обозначить `unknown`, разрешая обычную copy с явной обработкой ENOSPC, без обещания достаточного места. Если остаётся SSH exec fallback, выполнять его через общий coordinator с той же identity/auth policy; не создавать отдельный процесс с личным legacy ключом, как сейчас в `queryStorageSpaceViaSSH`. Не повторять операцию через ADB после неопределённого результата изменяющего SFTP запроса: сначала reconcile.
- Системный OpenSSH выполняет TCP, handshake, KEX, auth, encryption и SSH channel flow control. Не переносить эти слои в `SSHProtocolHandler.swift` без отдельного обоснованного проекта. `TCP_NODELAY`, cipher и channel window менять только тем способом, который доступен через OpenSSH/MINA и проверен по факту; не приписывать Swift-коду управление чужим TCP socket.
- `STATUS OK` для WRITE не равен физической durability. Обычное копирование не требует fsync после каждого файла; если вводится durable mode, в нём checkpoint и commit должны соответствовать реально поддерживаемому сервером fsync. Hash mode также только при доступном способе прочитать/вычислить remote hash; ограниченное сравнение первых 4 KiB не считать целостностью всего файла.
- Для download нужен локальный temp + final rename с проверкой и сохранением существующего final при ошибке; для upload — удалённый temp. Проверки размера перед и после commit не заменяют strong hash, но обязательны всегда.
- Не добавлять custom TAR, собственный listdir/events protocol, ручную реализацию SSH, Netty, `mmap`, обязательные direct buffers и TCP micro-tuning: они вне v1.

## Приёмка и формат отчёта

Собери macOS из `MacHost/`: `swift build`, `swift run MacHostTests` (это executable target, одного `swift test` недостаточно). Android из `AndroidCompanion/`: `./gradlew assembleDebug` и подходящие тесты. Выполни интеграционные тесты с реальным Android при наличии устройства. Если его нет, используй локальный SFTP server/fault injector; проверки MediaStore/HyperOS остаются незакрытыми воротами. Не называй такую сборку полной production-приёмкой.

Обязательные дополнительные сценарии: пустой файл и последний короткий chunk; fragmented/coalesced packets, `ATTR_EXTENDED` в NAME/ATTRS и `EXTENDED_REPLY`; ID wraparound и поздний ответ отменённой операции; заполнение обоих pipes; disk full/ошибка SQLite; source replacement; crash до/после checkpoint и rename; одновременные list/preview/bulk; переключение двух USB устройств с одинаковым loopback endpoint; отсутствие extension. Для normal copy проверить сетевой reconnect, для durable checkpoint — потерю процесса/перезагрузку и корректный порядок сохранения данных и журнала. Сохранить keepalive OpenSSH без второго дублирующего heartbeat; проверить transfer при выключенном экране Android и корректное освобождение wake lock после последнего активного channel.

По каждому этапу предоставь: список файлов и контрактов, миграцию journal/cache, выполненные тесты с результатами, baseline/после с условиями, оставшиеся ограничения, SHA коммита и тег ворот. В конце дай матрицу соответствия инвариантам, включая доказательство общего session budget, одного reader, корректного resume, атомарного commit и фактического числа SSH/TCP sessions/channels. Все решения, меняющие функциональность, внеси в README/архитектурную документацию и CHANGELOG.
