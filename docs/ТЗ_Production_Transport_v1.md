# ТЗ для модели-исполнителя: Production Transport v1

## Задача и источник

Реализуй в текущем MacDroid Commander устойчивый и измеряемый транспорт Mac ↔ Android на стандартном SSH/SFTP. Исходная концепция: `MacDroid — Production Transport Architecture v1` из приложенного пользователем плана. Этот документ адаптирует её к **текущему коду** и задаёт порядок работы, инварианты и проверяемые результаты. Перед правками прочитай исходный план, `README.md`, `docs/architecture_brief.md`, `docs/product_spec_v3.md` и актуальный код. Старый `docs/ТЗ_для_LLM.md` описывает прежний прототип и содержит устаревшие утверждения о mock-транспорте; не принимай его за описание текущего состояния.

Работай в корне репозитория. На момент составления этого ТЗ ветка `main` уже существовала, а пользовательские незакоммиченные изменения были в `ConnectionController.swift`, `DualPaneViewModel.swift`, `PaneView.swift`, `MacHost/Tests/MacHostTests/main.swift`. **Сначала повторно проверь `git status`**. Не сбрасывай, не stash и не включай чужие правки в свои коммиты. Отдельная ветка или worktree допустимы только с сохранением границ этих изменений. Каждый завершённый этап фиксируй отдельным коммитом; перед рисковыми переделками ставь тег. После изменения кода подними версии во всех связанных файлах версионирования (`MacHost/Resources/Info.plist`, `AndroidCompanion/app/build.gradle.kts`, а также других, если сборочные скрипты задают версию) и обнови документацию функциональности. Стадируй файлы выборочно.

Прямые вызовы `downloadFileStreaming` из `DualPaneViewModel` для preview/Quick Look учесть в приоритетах и в бюджете, а не только вызовы `JobOrchestrator`.

## Обязательные инварианты

1. Считывать байты из одного SFTP stdout вправе только один read loop. Для каждого ответа проверить framing, тип, `requestId`, принадлежность текущей session/channel и наличие pending operation. Неизвестный/дублированный ответ, неожиданный `STATUS` и EOF не могут ошибочно завершить другую операцию. `VERSION` обрабатывается отдельно до request dispatcher. Ограничить максимальный размер входного пакета до выделения памяти.
2. Ни один SSH/SFTP handle не переживает reconnect. При смене endpoint, host key или session epoch все pending запросы завершаются явной ошибкой, кредиты освобождаются один раз, новая session создаёт новые handles. Отмена одного transfer не уничтожает чужой незавершённый запрос; аварийное завершение общей session классифицирует все запросы.
3. Весь concurrency ограничен **общим** `SessionBudget`: байты в сети, удерживаемые write buffers, открытые handles, активные transfer и операции FS на Android. Кредит выдаётся до отправки, возвращается при ACK/ошибке/отмене/teardown ровно один раз. Интерактивным операциям оставить резерв и обеспечить, что большой bulk transfer не блокирует листинг/preview бесконечно.
4. `READ` и `WRITE` сопоставлять по ID с `{file, offset, requestedLength, epoch}`. Для short `DATA` повторно запросить остаток либо явно завершить ошибкой; нельзя зачесть недополученные байты. Ответы могут прийти вне порядка. Download пишет по смещению (`pwrite` или защищённый аналог); `written == expectedSize` само по себе не доказывает покрытие без дыр.
5. Progress для возобновления берётся из непрерывно подтверждённого диапазона, а не из размера `.mcdpart`, наибольшего ACK или числа отправленных байт. Для download подтверждение означает **успешную запись локального диапазона**; для upload — `STATUS OK` соответствующего `WRITE`. Различать ACK и durable checkpoint.
6. Upload пишется только в уникальный temp path, затем проверяется, закрывается и атомарно коммитится в final path. `COMPLETED` и удаление исходника при Move возможны лишь после подтверждения финального объекта. При overwrite сохранить семантику существующего backup/rollback; при невозможности гарантировать атомарное замещение или при неопределённом результате rename — состояние `INDETERMINATE`, без потери старой версии.
7. Кэш листинга служит только UI. `DELETE`, `RENAME`, `OVERWRITE`, `OPEN` и resume требуют актуальной проверки объекта. Ключ кэша включает SSH host-key fingerprint, идентификатор storage/volume и нормализованный path. Не показывать temp файлы как завершённые.

## Этапы реализации

### P0. Надёжная основа, до увеличения глубины конвейера

1. Зафиксируй исходные benchmark и тесты без правок кода; опиши реальные ограничения системного OpenSSH. Для двух SFTP channels в одной TCP/SSH session выбери и проверь практический механизм (например, OpenSSH multiplexing через выделенный ControlMaster/ControlPath и два `ssh -S ... -s sftp` процесса). Если выбранный механизм не доказан end-to-end с Android MINA, оставь один безопасный канал и пометь разделение channels как отдельный незакрытый критерий: не подменяй требование двумя независимыми TCP sessions. Не трогай пользовательские SSH config/key files.
2. Введи session-scoped dispatcher и typed request API вместо сочетания `sendSFTPPacket`, `writeRawPacket`, `readRawResponse` из разных компонентов. Сериализуй запись в pipe, создай один reader и pending map, тайм-ауты и deterministic teardown. Мигрируй все места в `TransportMultiplexer` и `RemoteSFTPDriver`; не оставляй обходных raw readers. Проверь handling `VERSION` и parse ошибок.
3. Добавь `SessionBudget` и byte-based backpressure с baseline: network in-flight 8 MiB, write buffers 8 MiB, handles 32, transfers 4 (max 8), interactive reserve 1 MiB. Для одиночного download стартуй с 128 KiB × 32 ≈ 4 MiB, upload с 128 KiB × 16 и high/low-water 4/2 MiB. Это стартовые настройки, не обещание скорости. Реальный chunk ограничивается `limits@openssh.com` при подтверждённой поддержке; без extension применяй проверенный безопасный предел и записывай fallback в telemetry. Server `window-size=8 MiB` уже задан; проверь фактические client/server window и packet sizes, не ставь 320 KiB вслепую на новых путях.
4. Сделай `ConfirmedRangeTracker` и отдельную durable таблицу/схему `TransferJournal` рядом с `IntentLedger` либо расширь его без нарушения текущих записей. Храни ID устройства/host key, direction, source snapshot, final/temp paths, expected size, диапазоны/frontier, state/epoch/commit marker. Записывай checkpoint атомарно. Определи policy flush и документируй, что после crash неперсистентные ACK переигрываются. Старым `.mcdpart` без journal не доверяй; разреши только безопасную проверку/restart, не удаляй пользовательские данные автоматически.
5. Приведи download и upload к циклу `prepare → transfer → drain → verify → close → commit → complete`; отдельно обработай cancel/retryable/fatal/indeterminate. Перед resume повторно проверь identity, размер, mtime и temp path; при расхождении верни `RESUME_CONFLICT`. Проверь случай crash между rename и записью `COMPLETED`: reconcile определяет результат по final/temp/backup, не повторяет опасный commit. Удали или переосмысли текущую очистку active `.mcdpart`, чтобы suspend/reconnect не уничтожали checkpoint.

**Ворота P0:** тесты с перестановкой ACK, дырой в диапазонах, short read, потерей соединения в каждой фазе, cancellation, stale handle, duplicate response, mismatch source/temp, повторным запуском после rename. Ни одна ошибка не превращается в успех; старая final версия сохраняется при неудачном overwrite. Поставь тег `gate-transport-p0` после зелёных тестов.

### P1. Производительность одиночных файлов и листинга

1. Увеличь глубину `READ`/`WRITE` только после P0, измеряя RTT, goodput и память. Буферы удерживаются до обработки конкретного ответа. Ни download, ни upload не держат весь файл в RAM.
2. `RemoteSFTPDriver.listDirectory` продолжает использовать attrs из `NAME`. Запрети N×`STAT` для уже предоставленных полей; отдельный `STAT` допускается лишь при недостающем атрибуте, который действительно нужен UI/операции.
3. Проверь конкурентные `READDIR` одного directory handle на Apache MINA SSHD 2.12.0 интеграционным тестом с 5 000+ уникальных записей, несколькими packet sizes, повторными прогонами и сверкой множества имён. До доказательства отсутствия пропусков/дублей оставь последовательный `READDIR`. Если он безопасен, включи depth 4 с feature flag и fallback. Не выдавай это за гарантированное свойство SFTP v3.
4. На Android ограничь FS executor (старт 4, максимум 8 операций) и очередь без unbounded накопления. Проверь API Apache MINA до выбора hook. Текущий `VirtualFileSystemFactory` сам по себе не заменяет FS listing на MediaStore.

**Ворота P1:** контрольные хэши/размеры после передачи, отсутствие стат-шторма, сохранность листинга, bounded memory/handles/FS ops и сравнение throughput с baseline P0 на том же устройстве и сети.

### P2. Android metadata acceleration

Добавь fast path MediaStore для допустимых каталогов `DCIM`, `Pictures`, `Movies`, `Music` только после проверки, что результаты соответствуют реальному `/storage`, разрешениям Android, nested folders, SD/OTG, Unicode и моменту обновления индекса. При неполном покрытии или ошибке MediaStore используй filesystem listing. Для остальных каталогов — bounded enumeration/attrs. Если нужен custom SFTP filesystem/accessor, реализуй его через поддерживаемый extension point MINA и тестируй обычный SFTP клиент; не расширяй wire protocol. Android SQLite/LRU metadata cache допустим для list, но операции над файлом валидируются через FS. Инвалидируй после commit/delete/rename/mkdir и внешних изменений настолько надёжно, насколько позволяют `FileObserver`/`ContentObserver`; TTL — safety net. Не подменяй точное состояние объекта устаревшей записью.

**Ворота P2:** одинаковые множества и атрибуты для 5 000 файлов при холодном/тёплом листинге, после внешней записи на телефоне, после операций MacDroid и после отключения/повторного подключения SD. Замерь latency MediaStore и FS fallback.

### P3. Отзывчивость и множество файлов

Реализуй macOS L1 memory + L2 SQLite directory cache со stale-while-revalidate, bounded TTL и invalidation после собственных операций. Не используй результаты старого устройства или сменённого host key. При refresh обновляй UI только при изменениях и защищай от ответа для уже покинутого каталога.

Для interactive/bulk traffic используй два доказанно отдельных SSH channels одной session, либо явно зафиксируй технический blocker и измеряемый временный режим с одним dispatcher и reserved credits. Не объявляй ворота P3 пройденными при двух TCP connections вместо одной session. Cross-file scheduler: 4 активных файла, максимум 8 по benchmark, общие byte/handle/FS кредиты, справедливость, отмена/пауза отдельного задания, сохранение порядка и conflict semantics. Файлы проходят собственные journal/commit независимо; group `COMPLETE` только после всех подтверждённых исходов.

**Ворота P3:** при копировании большого файла открытие каталога/preview имеет ограниченную и измеренную задержку; 1 000 малых файлов не создают неограниченных tasks/handles/буферов; pause/resume/cancel одной передачи не повреждают остальные.

### P4. Наблюдаемость и benchmark

Добавь счётчики и логирование без путей, имён файлов, ключей и содержимого по умолчанию: SFTP RTT, READ/WRITE throughput, in-flight bytes, queue wait, SSH channel stalls там, где OpenSSH даёт наблюдаемость, Android FS latency, MediaStore latency, активные FS ops, пиковая память buffers, reconnect, реально сохранённые resume bytes. Если метрику нельзя получить из системного `ssh` без смены transport, явно пометь недоступной; не выводи фиктивное значение. Сценарии: raw TCP, SSH stream, single large upload/download, 5 000-entry list, 1 000 small files, Wi-Fi loss/reconnect. Зафиксируй устройство, версию Android/macOS, USB или Wi-Fi, размер/число файлов, прогрев, несколько повторов, median и диапазон; сравни с исходным baseline. Не обещай конкретный множитель ускорения до замеров.

## Protocol и compatibility правила

- SFTP v3 остаётся базовым wire protocol. Возможности `limits@openssh.com`, `statvfs@openssh.com`, `posix-rename@openssh.com`, `fsync@openssh.com` и server-side hash обнаруживаются по `VERSION`/подтверждённому ответу, а не по предположению, что Android MINA поддерживает OpenSSH extensions. Отсутствие каждой возможности имеет явный fallback. `statvfs` не заменять фиктивным объёмом диска: текущий `RemoteSFTPDriver.checkFreeSpace` возвращает при провале произвольные 280/512 GB; исправить на явное `unknown`/ошибку с понятным поведением preflight.
- Системный OpenSSH выполняет TCP, handshake, KEX, auth, encryption и SSH channel flow control. Не переносить эти слои в `SSHProtocolHandler.swift` без отдельного обоснованного проекта. `TCP_NODELAY`, cipher и channel window менять только тем способом, который доступен через OpenSSH/MINA и проверен по факту; не приписывать Swift-коду управление чужим TCP socket.
- `STATUS OK` для WRITE не равен физической durability. Обычное копирование не требует fsync после каждого файла; если вводится durable mode, в нём checkpoint и commit должны соответствовать реально поддерживаемому сервером fsync. Hash mode также только при доступном способе прочитать/вычислить remote hash; ограниченное сравнение первых 4 KiB не считать целостностью всего файла.
- Для download нужен локальный temp + final rename с проверкой и сохранением существующего final при ошибке; для upload — удалённый temp. Проверки размера перед и после commit не заменяют strong hash, но обязательны всегда.
- Не добавлять custom TAR, собственный listdir/events protocol, ручную реализацию SSH, Netty, `mmap`, обязательные direct buffers и TCP micro-tuning: они вне v1.

## Приёмка и формат отчёта

Собери macOS (`swift build` и текущий test target), Android (`./gradlew assembleDebug` и подходящие тесты), выполни интеграционные тесты с реальным Android при наличии устройства. Если физического устройства нет, используй локальный тестовый SFTP server/fault injector для protocol и recovery, а проверки, требующие Android MediaStore/HyperOS, честно оставь как незакрытые ворота. Не называй такую сборку полной production-приёмкой.

По каждому этапу предоставь: список файлов и контрактов, миграцию journal/cache, выполненные тесты с результатами, baseline/после с условиями, оставшиеся ограничения, SHA коммита и тег ворот. В конце дай матрицу соответствия инвариантам, включая доказательство общего session budget, одного reader, корректного resume, атомарного commit и фактического числа SSH/TCP sessions/channels. Все решения, меняющие функциональность, внеси в README/архитектурную документацию и CHANGELOG.
