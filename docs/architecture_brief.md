# Architecture Brief
Составлено: 2026-09-01

---

## 1. Goal / User outcomes

Пользователь работает с файлами, расположенными в двух разных местах — на своём ноутбуке и на своём телефоне — из одного приложения на ноутбуке, без необходимости физически брать телефон в руки для большинства действий.

Пользователю доступно:
- Одновременный просмотр содержимого двух выбранных им расположений (каждое — либо на ноутбуке, либо на телефоне), рядом друг с другом.
- Независимый выбор для каждого из двух расположений: где именно смотреть (ноутбук или телефон) и какую папку внутри него; этот выбор сохраняется и восстанавливается при следующем открытии приложения.
- Копирование, перемещение, переименование, создание и удаление файлов и папок — как на ноутбуке, так и на телефоне, включая перенос между ними в обе стороны.
- Выделение сразу нескольких файлов/папок и совершение действия над всеми выделенными сразу.
- Сортировка и фильтрация видимого списка по имени, размеру, датам и типу.
- Просмотр изображений (включая формат HEIC) — как в виде миниатюр в списке, так и в полноэкранном режиме с перелистыванием, без выхода из приложения.
- Наблюдение за ходом длительных операций копирования (что происходит сейчас, сколько осталось) и возможность отменить операцию, пока она выполняется.
- Понятная реакция на нештатные ситуации (совпадение имён, потеря связи с телефоном, ошибка на одном из многих файлов) — без того, чтобы пользователь терял данные без предупреждения или получал противоречивую картину происходящего.
- После первой настройки связи с телефоном — последующие подключения происходят без повторного ввода пользователем данных для сопряжения.

## 2. Hard platform constraints

- Ноутбук — macOS. Приложение распространяется вне Mac App Store, то есть не обязано подчиняться правилам App Sandbox для доступа к произвольным файлам на диске ноутбука.
- На современных версиях macOS система запрашивает у пользователя явное разрешение, прежде чем приложение сможет обращаться к устройствам в локальной сети *(заполнить: точная версия macOS, с которой это действует, требует проверки)*.
- macOS предоставляет публичный способ переместить файл в Корзину (а не удалить его безвозвратно) программно.
- Телефон — Android (Xiaomi 14 Ultra, оболочка MIUI/HyperOS).
- Без root-доступа на телефоне сторонее приложение не может обращаться к внутренним данным других приложений на этом телефоне — это ограничение платформы, а не текущей реализации.
- Доступ стороннего приложения к файлам общего назначения на Android по умолчанию ограничен; получение более широкого доступа требует отдельного явного разрешения пользователя, которое площадка дистрибуции (Google Play) рассматривает как повышенный риск при модерации.
- У Android есть встроенный механизм «корзины» только для файлов, индексируемых системой как медиа (фото/видео/аудио, начиная с определённой версии ОS) — для произвольных файлов и папок общего назначения аналогичного системного механизма нет; удаление таких объектов необратимо на уровне платформы.
- Оболочка MIUI/HyperOS on этом конкретном устройстве управляет фоновыми процессами заметно агрессивнее, чем базовый Android: стандартных системных механизмов исключения приложения из энергосбережения может быть недостаточно, и обычно требуется дополнительное действие пользователя в настройках самой оболочки.
- Оба устройства должны находиться в зоне досягаемости друг друга по какому-либо каналу связи (например, в одной локальной сети) для взаимодействия в реальном времени; гарантированного способа обратиться к телефону, находящемуся вне досягаемости, не существует.
- Пропускная способность Bluetooth принципиально ограничена (на порядки ниже типичного Wi-Fi) — это физическое свойство технологии, а не деталь реализации.
- Файловая система телефона не гарантирует доступность поля «дата создания» файла через стандартные механизмы чтения метаданных; дата последнего изменения доступна значительно надёжнее.
- Оба устройства могут в любой момент быть недоступны друг для друга по не зависящим от приложения причинам (сон, смена сети, выключение экрана, выключение устройства).

## 3. Operational scenarios

1. Первый запуск приложения на ноутбуке — телефон ещё не был подключен ни разу.
2. Повторный запуск — телефон уже был подключен ранее и сейчас доступен в сети.
3. Повторный запуск — телефон был подключен ранее, но сейчас недоступен (выключен, другая сеть).
4. Пользователь переключает одно из двух расположений с папки на ноутбуке на папку на телефоне посреди работы.
5. Пользователь заходит в папку на телефоне, содержащую несколько тысяч файлов.
6. Пользователь выделяет несколько десятков файлов сразу на обоих расположениях и запускает перенос с телефона на ноутбук.
7. Во время переноса файла связь с телефоном на несколько секунд пропадает и затем восстанавливается сама.
8. Во время переноса файла экран телефона гаснет / приложение-компаньон на телефоне уходит в фон.
9. Пользователь отменяет уже начавшийся перенos нескольких файлов на середине.
10. Пользователь копирует файл, имя которого уже существует в целевом расположении.
11. Пользователь удаляет несколько выделенных файлов на телефоне за одно действие.
12. Пользователь удаляет несколько выделенных файлов на ноутбуке за одно действие.
13. Из 50 файлов, участвующих в одной операции копирования, один не может быть скопирован (нет прав, файл исчез, слишком длинное имя для целевой файловой системы), остальные 49 — успешно.
14. Пользователь листает подряд несколько фотографий, физически находящихся на телефоне, в полноэкранном режиме.
15. Ноутбук уходит в сон посреди незавершённого переноса файлов и позже «просыпается».
16. Пользователь запускает вторую операцию копирования, не дождавшись завершения первой.
17. Пользователь переименовывает на телефоне файл, который в этот момент уже выбран как источник для выполняющегося переноса.
18. Оба устройства физически рядом друг с другом, но не находятся в одной локальной сети.

## 4. Failure symptoms

Реальных зафиксированных случаев сбоев по этой системе на данный момент нет — система проектируется с нуля, эксплуатационная история отсутствует. Этот раздел сознательно оставлен пустым, а не заполнен предположениями.

---

## 5. Required invariants

- Ни одна операция копирования, перемещения или удаления не должна приводить к тихой потере данных: либо результат гарантированно доведён до подтверждённого состояния, либо пользователю явно показано, что он не завершён.
- Частично перенесённый файл ни при каких условиях не должен быть неотличим (ни для пользователя, ни для самой системы) от полностью перенесённого файла.
- Отмена операции в любой момент времени не должна оставлять файловую систему в состоянии, где невозможно понять, что было выполнено, а что — нет.
- Ошибка на одном объекте в многообъектной операции не должна прерывать обработку остальных объектов без явного индивидуального указания результата по каждому.
- Недоступность канала связи с телефоном должна быть отличима для пользователя от факта отсутствия файла/папки на телефоне — нельзя показывать «не существует», когда на самом деле «недоступно для проверки».
- Любые отображаемые сведения об удалённом расположении (список файлов, свободное место), полученные не в реальном времени, должны быть явно помечены как потенциально устаревшие, с указанием момента последнего обновления.
- Любое разрушительное действие (удаление, перезапись при конфликте имён) должно давать пользователю возможность увидеть, что именно будет затронуто, до того как действие станет необратимым.
- **Мета-инвариант.** Система не должна выдавать эвристическую оценку за гарантию. Там, где гарантия недостижима в принципе (например, абсолютное подтверждение, что удалённый файл не изменился за интервал между проверкой и началом операции), система обязана явно обозначить границу своей уверенности и перейти в явное неопределённое или ошибочное состояние — вместо того чтобы сообщить пользователю ложный успех.

## 6. Conceptual entities

Категории данных и связей — без имён компонентов и без предполагаемых границ ответственности между ними:

- Единица файловой системы (файл или папка) на одном из двух типов носителей.
- Расположение/источник данных — локальный (на ноутбуке) или удалённый (на телефоне).
- Метаданные единицы файловой системы: имя, размер, тип, дата изменения; опционально — дата создания, дата съёмки, если платформа их предоставляет.
- Текущий выбор пользователя внутри одной из двух областей просмотра: какое расположение показано, какой путь внутри него, в каком порядке и с какой фильтрацией отображаются объекты, видны ли скрытые объекты.
- Выделенное подмножество объектов, над которым пользователь совершает действие.
- Действие, изменяющее файловую систему одного или обоих расположений (копирование, перемещение, переименование, создание, удаление) — с указанием источника и цели.
- Длительный процесс переноса данных между расположениями, имеющий различимые промежуточные состояния (выполняется, приостановлен, завершён, прерван, завершён с ошибкой).
- Канал связи между ноутбуком и телефоном, доступность которого может меняться в любой момент независимо от действий пользователя внутри приложения.
- Однократно устанавливаемая и затем многократно используемая связь доверия между конкретным ноутбуком и конкретным телефоном.
- Локально сохранённое представление удалённого состояния (список объектов, их метаданные, изображения для предпросмотра), которое может расходиться с фактическим состоянием на телефоне в любой момент времени.
- Сообщение о результате завершённого действия или о конфликте, требующее решения пользователя.

## 8. Non-goals

*Заполнить: что именно сознательно исключается из этого захода проектирования — требуется уточнение у автора проекта. Кандидаты для рассмотрения: поддержка iPhone/iOS, синхронизация в реальном времени с отслеживанием изменений на обеих сторонах, редактирование файлов «на месте» (помимо просмотра изображений), одновременная работа более чем с одним телефоном, любые каналы связи, кроме основного сетевого.*

---

## 9. Existing implementation

Готовой реализации не существует; система проектируется с нуля, и предложенная архитектура не должна наследовать или предполагать какой-либо конкретный существующий код.

---

## 10. Expected architectural output

От каждой модели ожидается:

- Декомпозиция системы на составные части, с обоснованием каждой границы через перечисленные инварианты, ограничения платформы и операционные сценарии (не просто описание, а явная привязка «эта граница существует, потому что сценарий №… и инвариант №… этого требуют»).
- Явное указание главного архитектурного компромисса, включая худшие свойства выбранного решения — не только его преимущества.
- От 2 до 4 рассмотренных и сознательно отвергнутых альтернатив, с кратким объяснением, почему каждая была отклонена.
- Диаграммы, необходимые для сравнимости ответов между разными моделями (единый минимальный набор: структура компонентов/границ и хотя бы один сценарий во времени — например, поток операции переноса файла со сбоем и восстановлением).
- Стратегия сопоставления/проверки (correlation/verification) там, где система имеет дело с ненадёжным внешним источником истины — то есть с состоянием телефона и каналом связи с ним, которые могут меняться или пропадать независимо от приложения на ноутбуке.

## Требования к формату ответа моделей

Каждая модель, отвечающая на этот бриф, обязана:
- Не видеть решений других моделей и не подстраиваться под "очевидный" вариант.
- Начать ответ первой строкой вида: `<{Имя_модели}> START {текущее время YYYY-MM-DD HH:mm, Europe/Madrid}`
- Закончить ответ последней строкой вида: `<{Имя_модели}> END {текущее время YYYY-MM-DD HH:mm, Europe/Madrid}`
