# Система

MacDroid Commander: Mac (SwiftUI, `/Users/restart/Documents/GitHub/MacDroidCommander/MacHost`) подключается по SSH/SFTP к приложению-компаньону на Android (`/Users/restart/Documents/GitHub/MacDroidCommander/AndroidCompanion`, встроенный сервер Apache MINA SSHD 2.12.0, порт 2222, домашняя Wi-Fi сеть или `adb forward` по кабелю).

## Доверие в обе стороны
- **Ключ телефона (host key).** Генерируется компаньоном при первом запуске (`SimpleGeneratorHostKeyProvider`, файл `hostkey.ser` в данных приложения, ECDSA P-521). Mac закрепляет SHA256-отпечаток за устройством (`pinned_hosts.json`, `known_hosts` с `HostKeyAlias=dev_<суффикс отпечатка>`, `StrictHostKeyChecking=yes`). Пользователь сверяет отпечаток на экране телефона и в окне Mac.
- **Ключ Mac (client key).** На Mac два ключа:
  1. `~/.ssh/macdroid_id_ed25519` (OpenSSH-формат) — им входят процессы `/usr/bin/ssh` (ControlMaster и SFTP-каналы);
  2. «выделенный» Ed25519 ключ приложения (CryptoKit, файл в `~/Library/Application Support/MacDroidCommander/client_ed25519.key`) — им входит встроенный Swift-клиент SSH при сопряжении и проверке. Он же передаётся телефону командой `authorize_key` (миграция со старого ключа). В реестре устройства есть флаг `isMigratedToDedicatedKey`.
- **Сопряжение на телефоне.** Кнопка «Разрешить сопряжение на 60 секунд» открывает окно. Кнопка «Сбросить сопряжение» удаляет `authorized_keys` и закрывает живые сессии.

```kotlin
// AndroidCompanion/app/src/main/kotlin/com/macandroid/filemanager/server/EmbeddedServer.kt
publickeyAuthenticator = PublickeyAuthenticator { _, key, session ->
    var accepted = false
    synchronized(pairingLock) {
        val encodedKey = Base64.getEncoder().encodeToString(key.encoded)
        if (!authorizedKeysFile.exists() || authorizedKeysFile.length() == 0L) {
            // Первый ключ принимается только в окне сопряжения, окно закрывается сразу после записи.
            if (isPairingModeActive) {
                authorizedKeysFile.writeText(encodedKey + "\n")
                closePairingWindow()
                accepted = true
            }
        } else {
            // Последующие подключения должны совпадать с уже сохранёнными ключами.
            accepted = encodedKey in authorizedKeys || authorizedKeys.any { /* разбор строк ssh-... */ }
        }
    }
    // Право на authorize_key — только у сессий, принятых в окне сопряжения или вошедших сохранённым ключом.
    session.setAttribute(ENROLLED_SESSION_KEY, accepted)
    accepted
}
```

# Что произошло (31.10–9.11.2026)
1. Компаньон на Xiaomi переустановили (обновление 2.1.18 → 2.1.19, вероятно через удаление). Данные приложения пропали: новый host key (`SHA256:E4p4f4…` → `SHA256:9Nuh43…`), пустой `authorized_keys`.
2. Mac принял новый отпечаток (пользователь подтвердил сброс ключа в окне Mac, 9.11 11:57), но войти не мог: оба ключа Mac получали `Permission denied (keyboard-interactive,publickey)`. Сообщения у пользователя при этом были о сетевой ошибке (отдельная проблема macOS), поэтому причина отказа в интерфейсе не была видна.
3. Пользователь нажал «Разрешить сопряжение на 60 секунд» и PHONE на Mac — не помогло. Вероятная причина по коду: в `authorized_keys` к этому времени уже был какой-то ключ (не установлено чей — возможно, другой копии приложения или агента), а окно сопряжения принимает ключ только при пустом файле. Об этом ничего не сообщается ни на телефоне, ни на Mac.
4. После «Сбросить сопряжение» + окно + PHONE (точная последовательность не зафиксирована) в 19:05 вход прошёл ключом `~/.ssh/macdroid_id_ed25519`.

# Вопросы
1. Оцени модель угроз текущей схемы: домашняя Wi-Fi сеть, атакующий в той же сети; кабель. Насколько безопасно правило «первый ключ — только при пустом `authorized_keys` и открытом окне»? Что даёт и чего не даёт сверка отпечатка host key глазами?
2. Правильно ли, что открытое окно сопряжения не добавляет новый ключ, если уже есть другой? Предложи схему, при которой в открытом окне пользователь может добавить ключ ещё одного Mac (или заменить старый) без полного сброса, и при этом атакующий в сети не может пролезть за эти 60 секунд. Например: подтверждение на экране телефона с отпечатком ключа Mac, короткий код подтверждения, ограничение «один ключ за окно».
3. Два клиентских ключа на Mac (OpenSSH-ключ и выделенный CryptoKit-ключ с миграцией через `authorize_key`) — это источник рассинхрона. Как упростить до одного ключа без потери уже сопряжённых устройств? Как безопасно перейти?
4. Переустановка компаньона: как Mac должен это распознавать (сменился host key, доверие пропало) и вести пользователя за один шаг, а не через сетевую ошибку? Нужен ли отдельный статус «Телефон не знает этот Mac — откройте сопряжение на телефоне»? Как отличить это от смены ключа атакующим?
5. Что телефон должен показывать в окне сопряжения: число сохранённых ключей, отпечатки, «ключ отклонён: окно открыто, но уже есть ключ X»? Какой минимум информации достаточен, чтобы пользователь сам понял, что делать?
6. Нужно ли переживать переустановку: хранить host key и `authorized_keys` в Android Keystore или резервной копии (Auto Backup), чтобы после обновления APK доверие сохранялось? Риски такого решения?
