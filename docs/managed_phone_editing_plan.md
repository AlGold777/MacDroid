# Управляемое редактирование файлов телефона — план на октябрь 2026

## Цель и инварианты
Открыть файл телефона в редакторе Mac, сохранить изменения в редакторе, увидеть состояние рабочей копии и явно отправить нужную версию обратно. Никакой автоматической перезаписи оригинала, потери локальных правок при отключении, путаницы одинаковых имён или записи на другое устройство.

## Архитектура
- Постоянное хранилище Application Support/MacDroidCommander/ExternalEdits/<UUID> вместо общего временного каталога. Сессия связывает UUID, стабильную идентичность устройства (закреплённый SSH fingerprint), исходный путь, локальный файл, исходный SHA-256 и последний подтверждённый SHA-256 отправленной копии.
- Оба способа открытия используют один механизм. Повторное открытие той же сессии использует существующую рабочую копию. Разные пути и устройства изолированы.
- Реестр записывается атомарно до передачи файла редактору; при перезапуске сессии восстанавливаются. Повреждённый реестр не заменяется пустым, файлы сохраняются для восстановления.
- Обнаружение изменений учитывает atomic-save (замену inode), удаление и возвращение файла. Сверка содержимого выполняется вне главного потока. NSFilePresenter полезен для редакторов с NSFileCoordinator, но сам по себе не покрывает низкоуровневую запись; необходима дополнительная сверка.
- Отправляется отдельный согласованный снимок, а не изменяемый редактором файл. Правки во время передачи остаются несохранёнными относительно отправленного снимка.
- Интерфейс «Рабочие копии»: исходный путь/устройство, состояния проверки, изменений, отправки, ошибки и подтверждённый путь результата; открыть редактор, показать в Finder, проверить изменения, сохранить копию на телефон. Без модальных запросов на каждое сохранение редактора.

## Этап 1 — безопасная полезная поставка
Постоянные сессии, единое открытие, восстановление, проверка SHA-256 по явной команде и при возврате фокуса/открытии списка. Явное сохранение рядом с оригиналом под уникальным именем `name.edited-<UUID>.ext`. Исходный файл не изменяется. Для передачи: EXCL-создание уникальной части, подтверждённый WRITE/CLOSE, SHA-256 части, обычный SFTP RENAME без перезаписи (не posix-rename), SHA-256 результата. До передачи проверяется закреплённый ключ устройства, захватывается канал; при смене устройства операция не перенаправляется. При неопределённом результате показывается целевой путь и сохраняется локальная версия, успех не объявляется. Повторная попытка создаёт новое имя; возможную копию с прошлого неопределённого исхода приложение не удаляет.

Приёмка: одинаковые имена в разных каталогах; повторное открытие; атомарное сохранение; отсутствие/возвращение локального файла; рестарт; offline/другое устройство; изменение во время передачи; нулевой и большой файл; отказ OPEN/WRITE/CLOSE/RENAME/VERIFY. Оригинал телефона побайтово неизменен.

## Этап 2 — замена оригинала с контролем конфликтов
Требует отдельного контракта Companion и согласования возможностей файловой системы. Ввести prepare/commit/status с idempotency key, исходной ревизией, хэшем содержимого и идентичностью устройства. Сервер сериализует свои записи, проверяет ревизию и атомарно публикует снимок; неподконтрольные записи других Android-приложений требуют проверяемого механизма блокировки/ревизий либо явного ограничения гарантий. Отдельная проверка SHA-256 на клиенте + posix-rename не являются compare-and-swap.

Конфликт: сохранить обе версии, скачать актуальную для сравнения или явно заменить после просмотра. Удалённый/переименованный оригинал не воссоздавать молча. Без поддерживаемой гарантии предлагать только сохранение отдельной копии. Journal на обеих сторонах различает not committed/committed/indeterminate и позволяет узнать исход после разрыва связи без повторной записи.

## Этап 3 — жизненный цикл и удобство
Наблюдение за каталогами с debounce и периодической контрольной сверкой; ограничение параллелизма/размеров, прогресс и отмена; сравнение трёх версий, выбор редактора, экспорт на Mac, доступность и локализация. Закрытие сессии и очистка — только явное действие с защитой несохранённых правок. Автоочистка исключительно подтверждённых закрытых сессий с сроком хранения. Не удалять активную рабочую копию: внешний редактор может сохранить её позже.

## Проверки и выпуск
Тесты состояния/хранилища и отказов транспорта, затем сборка бандла, ручная проверка актуального единственного процесса и версии UI, проверка с реальным телефоном, фиксация фактических ограничений. Все проверки делегируются GPT-6 Luna / high. Каждый законченный этап — отдельный коммит, версия, документация, backup с одноимённым Git tag.

## Первичные источники
- Apple NSFilePresenter: https://developer.apple.com/documentation/foundation/nsfilepresenter — уведомления покрывают координированные обращения, не все низкоуровневые записи.
- SFTP v3 draft, §6.5: https://www.ietf.org/archive/id/draft-spaghetti-sshm-filexfer-00.html — обычный RENAME должен отказать при существующей цели; CREATE|EXCL защищает существующий файл.

## Состояние реализации
План зафиксирован отдельным коммитом до реализации. В 2.1.279 реализован этап 1: ExternalEditStore, ExternalEditManager, окно рабочих копий, единый путь открытия и publishEditedCopy с проверкой закреплённого ключа, отдельным снимком и проверкой SHA-256 до/после RENAME. Замена оригинала и автоматическое фоновое наблюдение относятся к последующим этапам. Неподтверждённые попытки не удаляются; повторная отправка сохраняет прежние пути для разбора.

Проверки GPT-6 Luna / high: ExternalEditTests (22 проверки), ContentToolsTests и MacHostTests (69 suites) прошли. Live phone suite в MacHostTests пропущен: localhost:2222 отказал в SSH-аутентификации; это не подтверждает сквозную отправку на телефон. Ручная проверка UI и результаты финальной сборки фиксируются отдельно после их завершения.
